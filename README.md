# Биржа номеро-ночей — демо

React-приложение, демонстрирующее покупку и продажу гостиничных номеро-ночей. Администратор выпускает тикер,
пользователь покупает его, видит в портфеле и продаёт обратно. Всё работает в браузере: вход, деньги, активы и
сделки демонстрационные.

Одна единица тикера — право на одну ночь в номере определённой категории конкретного отеля на конкретную дату.
`AURORA-STD-20261015` — стандартный номер в отеле Aurora на ночь с 15 на 16 октября 2026 года.

## Быстрый старт

Нужен Node.js 22+.

```bash
npm ci                    # зависимости строго по package-lock.json
npm run dev               # http://localhost:5173
```

Production-сборка:

```bash
npm run build             # проверка типов + сборка в dist/
npm run preview           # локальный просмотр dist/
```

## Публикация

Приложение публикуется на GitHub Pages: https://objnamegit.github.io/hotel-service/

Workflow `.github/workflows/deploy.yml` на каждый push в `main` прогоняет lint, typecheck, unit- и e2e-тесты,
собирает приложение с `BASE_PATH=/<имя-репозитория>/` и публикует `dist/`. Прямые ссылки вроде `/market` работают
через `404.html` — копию `index.html`. Для первого запуска в настройках репозитория нужно выбрать
**Settings → Pages → Source: GitHub Actions**.

Локально проверить сборку в подпапке:

```bash
BASE_PATH=/hotel-service/ npm run build
BASE_PATH=/hotel-service/ npm run preview   # http://localhost:4173/hotel-service/
```

## Архитектура

Зависимости направлены строго внутрь: `pages → features → stores → services → domain`. Страницы и компоненты не
работают с `localStorage` и не содержат торговой логики.

```
src/
├── domain/          Чистая логика без React и хранилищ
│   ├── money.ts           копейки, разбор ввода без float, форматирование
│   ├── calendar-date.ts   даты YYYY-MM-DD в локальном календаре, без UTC
│   ├── trading.ts         quoteTrade / executeTrade — правила сделок (иммутабельно)
│   ├── exchange-state.ts  инварианты: доступно + в портфеле = выпущено
│   ├── validation.ts      Zod-схемы, общие для формы и сервиса
│   └── seed.ts            начальное состояние
├── services/        Типизированный асинхронный сервис
│   ├── exchange-service.ts   контракт ExchangeService (вход, тикеры, портфель, buy/sell, сброс)
│   ├── errors.ts             ServiceError с кодами и ошибками полей
│   └── local/                локальная реализация: localStorage + sessionStorage
├── stores/          Zustand: кеш данных и действия поверх сервиса (фабрики — для тестов)
├── features/        Функциональные блоки UI: auth, tickers, market, trade, order-book, portfolio, demo
├── pages/           Тонкие страницы маршрутов, загружаются лениво
├── app/             Роутер, guard'ы ролей, лейауты, провайдеры
└── components/      Общие компоненты; components/ui — shadcn/ui
```

Ключевые решения:

- **Сервис как граница.** UI зависит только от интерфейса `ExchangeService`. Чтобы подключить HTTP API, достаточно
  написать ещё одну реализацию и вернуть её из `createExchangeService()` в `src/services/index.ts`.
- **Атомарные сделки.** Сервис читает состояние, заново проверяет ограничения чистой функцией `executeTrade` и
  сохраняет баланс, позицию и остаток одной записью. При ошибке ничего не пишется. Перед записью проверяются
  инварианты.
- **Защита от повторной отправки** на трёх уровнях: кнопка блокируется, повторный клик отсекается синхронным флагом, а
  у каждой подтверждённой операции есть `operationId`, повтор которого сервис отклоняет. Операции записи
  сериализуются, а между вкладками — через Web Locks API.
- **Версионированное хранение.** Данные лежат в `localStorage` в конверте `{ version, data }` и при чтении проходят
  через миграции (`STATE_MIGRATIONS`), Zod-схему и проверку инвариантов. Если данные повреждены или несовместимы,
  появляется диалог со сбросом. Демо-сессия хранится в `sessionStorage`.
- **Синхронизация вкладок.** Изменения из другой вкладки приходят через событие `storage` (`service.subscribe`).
- **Деньги** хранятся целыми копейками, **количества** — целыми числами, **даты ночей** — строками `YYYY-MM-DD`.

## Web3 Order Book (платный блок shadcn.io)

По ТЗ стакан должен использовать исходный блок
[Web3 Order Book](https://www.shadcn.io/blocks/web3-order-book) с shadcn.io. Блок платный: реестр отдаёт его
только по токену, доступ предоставляет заказчик.

**Текущее состояние:** токена при разработке не было, поэтому исходный блок **не установлен**. На его месте стоит
явно помеченная временная заглушка (`src/features/order-book/order-book-fallback.tsx`) с предупреждением прямо в
интерфейсе. Это не замена блока. Сценарий приёмки 9 выполнится только после установки блока; соответствующий
e2e-тест до тех пор пропускается с пояснением.

Установка:

```bash
export SHADCN_IO_TOKEN=<токен из https://www.shadcn.io/dashboard/account>
npm run blocks:order-book
```

Реестр `@shadcnio` уже настроен в `components.json` и передаёт токен заголовком `Authorization: Bearer`. После
установки:

1. В `src/features/order-book/order-book-view.tsx` сопоставить `DemoOrderBookData` с props блока: пять уровней
   `bids` и `asks` с ценой, количеством и глубиной, спред. Выставить `ORDER_BOOK_SOURCE = 'shadcn-io'`.
2. Удалить `order-book-fallback.tsx`.
3. Адаптировать блок под Vite: убрать `"use client"` и Next-специфичные импорты, если они есть; структуру и
   визуализацию сохранить.

Данные стакана генерирует `generateOrderBook()`: пять уровней покупки и пять продажи вокруг цены тикера, со
стабильным сидом из идентификатора тикера. Таймеров и симуляции нет. Стакан не является источником цены и не
ограничивает объём сделок. Над ним всегда выводится подпись «Демонстрационный стакан. Сделки исполняются по
фиксированной цене».

## Проверки и сценарии приёмки

| Сценарий ТЗ                                                              | Где проверяется                                                  |
| ------------------------------------------------------------------------ | ---------------------------------------------------------------- |
| 1. Вход обеих ролей, выход, ограничения маршрутов                        | `e2e/auth.spec.ts`, `local-exchange-service.test.ts`             |
| 2. Созданный тикер виден на рынке после смены роли                       | `e2e/admin.spec.ts`                                              |
| 3. Дубликат кода, прошедшая дата, отрицательная цена, дробное количество | `e2e/admin.spec.ts`, `create-ticker-form-schema.test.ts`, сервис |

| 6. Продажа части и всей позиции                                          | `e2e/trading.spec.ts`, `trading.test.ts`                         |
| 7. Продажа сверх позиции, повторная отправка                             | `e2e/trading.spec.ts`, сервис (параллельные запросы)             |
| 8. Сохранение после перезагрузки, сброс                                  | `e2e/trading.spec.ts`, сервис                                    |

проверяется и в unit-, и в e2e-тестах.

## Ограничения демо

- Нет backend, реальных платежей, бронирования, интеграций с отелями и блокчейна.
- Авторизация и проверка ролей клиентские. Они служат поведению демо и не защищают данные: всё хранится в
  `localStorage` этого браузера.
- Цена тикера фиксированная. Комиссий, частичного исполнения, лимитных заявок и коротких продаж нет.
- Редактирование, дополнительный выпуск и удаление тикеров не реализованы: создание окончательное.
- Активы не погашаются автоматически при наступлении даты проживания.
- Стакан — статичная визуализация, не связанная с исполнением сделок.
